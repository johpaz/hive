02 · Request lifecycle

What happens on one run

From a message landing in a channel to an independently verified result — the same ten steps whether the trigger is chat, cron, or a task-graph node.

1

hive start / hive dev launches the gateway — gateway/server.ts's startGateway().

2

Gateway boots HiveDB, the ChannelManager, AgentService, the durable job queue + executors, the cron/DAG scheduler, canvas, and voice/multimodal services.

3

~20 REST route modules are registered and the pre-built hive-ui SPA is served from the same process.

4

Inbound channel messages, webchat turns, and cron/DAG triggers become jobs — chat_turn, goal_run, project_task, worker_task — on the durable queue.

5

The coordinator handles simple work itself. Otherwise it retrieves a specialist by task description and delegates a bounded subtask with context and explicit acceptance criteria; the free worker covers unmatched work.

6

specialist-runtime wakes the dormant template with its exact prompt, tool allowlist, skills and model policy, then connects only authorized MCP servers lazily.

7

The Native Agent Loop executes it while run-store and the durable queue checkpoint leases, idempotency and retries in HiveDB.

8

acceptance_verifier independently checks every criterion against evidence and persists a VerificationDoc. Missing evidence fails closed and returns to execution.

9

Only verified work produces a ProofPacketDoc. Traces attributed by specialist_id feed the specialty's ACE playbook and health counters.

10

The coordinator reports the result. The specialist hibernates and its lazy MCP connections are released after TTL.

03 · Dormant capability pool

Specialists wake only when the task needs them

Routing descriptions are intentionally short and concrete for local 7B models. Templates live in HiveDB; sleeping specialists consume no model or MCP resources.

Independent acceptance verifier

Never performs the original task. It inspects the requested outcome, criterion-level evidence and risks, then emits pass, fail or needs-input. The coordinator cannot report success without its persisted approval.

Lifecycle & isolation

select → wake → execute → verify → prove → hibernate. Repeated compatible tasks reuse a warm specialist; distinct specialists may run in parallel on independent queue lanes.

ACE learns the structure

Per-specialist traces update playbooks. The Curator proposes tool moves, new specialties for recurring free-worker patterns, and deactivation when harmful evidence outweighs helpful evidence.

08 · Current architecture

v0.0.47 — the specialist hive

Dormant specialists & an independent acceptance gate

package 0.0.47 working-tree architecture

The Native Agent Loop now supports a learnable local-first hive: one user-facing coordinator, 13 dormant specialist templates, scoped tools/skills/MCP, durable execution and independent criterion-level verification before any promise of success.

specialist-catalog / selector13 typed templates and BM25/hybrid routing from plain-language task descriptions.
specialist-runtimeexact loadout materialization, stable warm-context reuse and lazy MCP lifecycle.
acceptance-verifierindependent fail-closed verdict with criterion-level evidence persisted as VerificationDoc.
context-compiler7B-friendly routing/decomposition protocol; only the coordinator may ask or answer the user.
job-executorsverification is a hard gate before completion and proof-packet generation.
HiveDB collections / indexes / seedspecialists, verifications and proposals are typed, searchable and seeded idempotently.
Curator / ACEper-specialty learning can move tools, propose recurring specialties or deactivate harmful ones.
free workerpreserved as the fallback for rare tasks that do not justify a forced taxonomy.
